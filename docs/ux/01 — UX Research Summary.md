## 1. الهدف من الوثيقة

هذه الوثيقة تدرس مستخدمي الميزة وأهدافهم ونقاط الاحتكاك المحتملة، بما يخدم تصميمًا عمليًا يُحوَّل مباشرة إلى Blazor دون إعادة تفكير أثناء البرمجة. كل ملاحظة هنا مستندة إلى نص حرفي في `task.pdf` أو إلى قرار تصميمي موثق؛ لا توجد أي Persona تسويقية أو بيانات مستخدم مخترعة.

## 2. المستخدمون المذكورون في التحليل

يحدد التحليل (الملخص، ص3) مستخدمين اثنين فقط، ويؤكد قسم الصلاحيات (C2) أن «إدارة المستخدمين والصلاحيات الكاملة خارج نطاق MVP»، كما أن مخطط Component المعتمد ينص صراحة: «موظف المخزون / مدير النظام — Authorization خارج نطاق MVP». لذلك لا يفترض هذا التصميم أي اختلاف سلوكي أو صلاحيات مختلفة بين الاثنين في الواجهة.

| المستخدم | الهدف (من التحليل) | المهام | البيانات المطلوبة |
|---|---|---|---|
| **موظف المخزون** (Actor في UC-001) | تسجيل الكميات الفعلية للمخزون في المخازن عند بداية تشغيل النظام (الملخص، ص3) | فتح الشاشة (UC-001)، إدخال الرأس (UC-002)، إضافة/تعديل/حذف السطور (UC-003..008)، الحفظ (UC-009) | قوائم Product وWarehouse (أسماء — BR-06)، حقول الرأس (رقم الوثيقة، التاريخ، المستخدم، البيان)، حقول السطر (الكمية، السعر، تاريخ الصلاحية) |
| **مدير النظام** | نفس المهام في نطاق MVP (لا FR/UC يميز أدوارًا) | نفس مهام موظف المخزون | نفس البيانات |

> **Design Decision UX-1:** المعاملتان بواجهة واحدة موحدة دون أي عناصر صلاحيات، لأن التحليل لا يعرّف أي اختلاف سلوكي. لو ظهر تمييز لاحق في تقييم المشروع فهذا قرار تصميمي معلَن قابل للتتبع، لا إغفال.
>
> **المصدر:** الملخص (ص3) + C2 + مخطط Component المصحح (البند 9).

## 3. User Profiles العملية

### 3.1 موظف المخزون / مدير النظام (نفس الملف الوظيفي)

**الهدف:** إدخال رصيد افتتاحي صحيح (رأس + سطور) للمخازن عند بدء تشغيل النظام، والتأكد من حفظه دون فقدان بيانات (UC-009: «ensuring accuracy and no loss»).

**المهام التي ينفذها (UC-001..009):**

| المهمة | UC | سلوك UX المطلوب |
|---|---|---|
| فتح شاشة الأرصدة الافتتاحية من القائمة الرئيسية | UC-001 | شاشة فارغة جاهزة + تحميل قوائم Product/Warehouse |
| إدخال رأس الوثيقة (رقم، تاريخ، مستخدم، بيان) | UC-002 | حقول واضحة + تحقق فوري (رقم الوثيقة، تاريخ صالح) |
| إضافة سطر رصيد جديد | UC-003 | سطر إدخال مدمج أعلى الجدول + زر Add |
| اختيار Product | UC-004 | قائمة منسدلة بأسماء الأصناف (Mock Data) — لا معرفات |
| اختيار Warehouse | UC-005 | قائمة منسدلة بأسماء المخازن (Mock Data) — لا معرفات |
| إدخال الكمية والسعر وتاريخ الصلاحية | UC-003/قسم 6.7 | الكمية مطلوبة (>0 — BR-02)؛ السعر والصلاحية اختياريان (6.7) |
| عرض السطور الحالية | UC-006 | جدول يظهر كل السطور بأسماء Product/Warehouse |
| تعديل سطر | UC-007 | فتح السطر للتعديل + إلغاء يعيد البيانات الأصلية |
| حذف سطر | UC-008 | ConfirmDialog قبل الحذف |
| حفظ الوثيقة | UC-009 | تحقق شامل ثم رسالة نجاح/خطأ |

**البيانات التي يحتاجها:** الأسماء الظاهرة (BR-06) وليس المعرفات الداخلية؛ مثال التحليل: Laptop HP، المخزن الرئيسي، كمية 50، سعر 500 (قسم 6.7).

**نقاط الاحتكاك المحتملة (مشتقة حرفيًا من المسارات البديلة):**

1. **رقم الوثيقة مكرر أو تاريخ غير صالح** (UC-002 A2/A3، UC-009 A1) — منع الحفظ.
2. **سطر بلا Product/Warehouse/كمية** (BR-01/BR-04/BR-05) — منع الإضافة.
3. **كمية ≤ 0** (BR-02، مثال التحليل: Quantity = -5) — رسالة خطأ.
4. **حفظ بلا سطور** (UC-009 A2) — رسالة «يجب إضافة صنف واحد على الأقل».
5. **حذف صف مفقود** (UC-008 A2) — رسالة مناسبة دون تغيير.
6. **فشل حفظ داخلي (Mock Data)** (UC-009 A4) — رسالة «تعذر حفظ الأرصدة الافتتاحية» + إعادة المحاولة.
7. **فشل تحميل القوائم** (UC-001 Alternate Flows) — رسالة + عدم الانتقال.

**ما الذي يجب أن يكون واضحًا له مباشرة:**

- أن الكمية مطلوبة وأكبر من صفر (BR-02).
- أن Product وWarehouse اختيارات إجبارية (BR-01/BR-04/BR-05).
- أن السعر وتاريخ الصلاحية اختياريان (قسم 6.7).
- أن الأسماء تظهر بدل المعرفات (BR-06).
- أن البيانات محفوظة داخل الجلسة فقط ولا يوجد حفظ خارجي (FR-09) — لا زر «التصدير» أو «قاعدة البيانات».
- أن الحذف يتطلب تأكيدًا (FR-08/UC-008).

> **Design Decision UX-2:** لا تُبنى أي عناصر توحي بوجود قاعدة بيانات أو تصدير (بدون أيقونات DB، بدون «Sync»)، لأن FR-09 يحصر التخزين داخل الجلسة.
>
> **المصدر:** FR-09 + UC-001..009 بمساراتها البديلة.

## 4. متطلبات UX الحاكمة من NFRs

| NFR | الأثر المباشر على UX |
|---|---|
| NFR-01 (متجاوبة، سريعة، بسيطة، ألوان متسقة) | تصميم بسيط بدون زخرفة؛ تخطيط ثابت وسريع الاستجابة |
| NFR-02 (عربية كاملة + RTL في كل العناصر) | RTL معالج من مستوى التخطيط: أزرار، حقول، جداول، Dialogs، محاذاة النصوص |
| NFR-03 (تحميل سريع، بلا تجميد عند الإضافة/التعديل) | لا Modals ثقيلة ولا إعادة تحميل صفحة؛ الإضافة والتعديل في نفس الشاشة فوريًا |
| NFR-04 (رسائل واضحة، تحقق سريع، تلميحات خطأ واضحة) | رسائل Inline قرب الحقل المعيب + Global Message أعلى الصفحة؛ تحقق عند Add وعند Save |
| NFR-06 (مؤشرات خطأ بارزة) | حقول معيبة بحدود حمراء + أيقونة/نص خطأ ظاهر |
| NFR-05 (قابلية التوسع) | بنية مكونات منفصلة (Component Spec في 07) |

## 5. القيود الصريحة (ما لا يُبنى في UX)

لا يُبنى: Dashboard، Reports، بحث متقدم، Pagination (لا نص يدعمها — تفاصيل MVP قليلة)، Authentication UI (C2)، Authorization UI، Notifications، Audit، أو أي شاشة غير شاشة الأرصدة الافتتاحية. تحسين تجربة الاستخدام مسموح **داخل** الوظائف الموجودة فقط.

## 6. خلاصة UX

تجربة الاستخدام المستهدفة: موظف مخزون يفتح شاشة واحدة، يكمل رأسًا من أربعة حقول، يضيف سطورًا في سطر إدخال دائم أعلى الجدول (Product، Warehouse، الكمية، السعر الاختياري، تاريخ الصلاحية الاختياري)، يرى السطور فورًا بأسمائها في الجدول، يعدل أو يحذف بأمان، ثم يحفظ برسالة تحقق شاملة واضحة. كل رسالة خطأ مبنية على مسار بديل موثق في التحليل، وكل عنصر UI قابل للتتبع إلى FR/UC/BR محدد.
