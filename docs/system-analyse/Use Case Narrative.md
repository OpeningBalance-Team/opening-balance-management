## UC-001 — فتح شاشة الأرصدة الافتتاحية للمخزون

| الحقل | التحليل |
| --- | --- |
| **Use Case ID** | `UC-001` |
| **Use Case Name** | فتح شاشة الأرصدة الافتتاحية للمخزون |
| **User Story** | بصفتي موظف مخزون أو مدير نظام، أرغب في فتح شاشة الأرصدة الافتتاحية حتى أتمكن من إدخال ومراجعة أرصدة الأصناف الموجودة في المخازن عند بداية استخدام النظام. |
| **Actor** | المستخدم (موظف المخزون / مدير النظام). |
| **Preconditions** | أن يكون المستخدم لديه صلاحية الدخول إلى النظام؛ أن يكون المستخدم داخل النظام؛ توفر شاشة الأرصدة الافتتاحية ضمن قائمة النظام. |
| **Trigger** | اختيار المستخدم خيار الأرصدة الافتتاحية للمخزون من قائمة النظام. |
| **Main Flow** | 1. يقوم المستخدم بفتح قائمة المخزون.؛ 2. يختار الأرصدة الافتتاحية.؛ 3. يقوم النظام بتحميل شاشة الأرصدة الافتتاحية.؛ 4. يعرض النظام نموذج بيانات الوثيقة `Header`، ويحتوي على رقم الوثيقة والتاريخ والمستخدم والبيان.؛ 5. يعرض النظام جدول تفاصيل الرصيد `Details`.؛ 6. يقوم النظام بتحميل البيانات الوهمية للأصناف والمخازن لاستخدامها في عمليات الإدخال.؛ 7. تصبح الشاشة جاهزة لاستقبال عمليات المستخدم مثل إضافة صنف أو تعديل البيانات. |
| **Alternate Flow A1** | **فشل تحميل الشاشة:** يحاول النظام تحميل الشاشة؛ يحدث خطأ في تحميل المكونات؛ يعرض النظام رسالة: «تعذر تحميل الشاشة، حاول مرة أخرى». |
| **Alternate Flow A2** | **عدم توفر بيانات الأصناف أو المخازن:** يفتح المستخدم الشاشة؛ لا توجد بيانات `Mock Data` متاحة؛ يعرض النظام رسالة توضح عدم توفر البيانات. |
| **Postconditions** | تم فتح شاشة الأرصدة الافتتاحية بنجاح؛ أصبحت مكونات الشاشة جاهزة للاستخدام؛ تم تحميل بيانات الأصناف والمخازن الوهمية. |
| **Functional Requirements** | يجب أن يوفر النظام إمكانية الوصول إلى شاشة الأرصدة الافتتاحية؛ يجب عرض بيانات `Header` الخاصة بالرصيد؛ يجب عرض جدول `Details`؛ يجب تحميل بيانات الأصناف والمخازن لاستخدامها في الإدخال. |
| **Non-Functional Requirements** | يجب أن يتم تحميل الشاشة خلال وقت مناسب؛ يجب أن تكون الواجهة سهلة الاستخدام؛ يجب أن تكون الشاشة متوافقة مع أحجام الشاشات المختلفة `Responsive`؛ يجب أن تدعم اللغة العربية واتجاه `RTL`. |
| **Acceptance Criteria** | عند اختيار الأرصدة الافتتاحية تظهر الشاشة بنجاح؛ تظهر جميع عناصر `Header` و`Details`؛ تظهر قوائم الأصناف والمخازن عند الحاجة؛ لا تظهر أخطاء للمستخدم أثناء فتح الشاشة. |
| **Assumptions** | المستخدم لديه صلاحية الوصول للشاشة؛ بيانات الأصناف والمخازن سيتم توفيرها عن طريق `Mock Data` وليس قاعدة بيانات؛ لا توجد عمليات حفظ دائمة في هذه المرحلة. |

## UC-002 — إدخال بيانات رأس الرصيد الافتتاحي

| الحقل | التحليل |
| --- | --- |
| **Use Case ID** | `UC-002` |
| **Use Case Name** | إدخال بيانات رأس الرصيد الافتتاحي |
| **User Story** | بصفتي موظف مخزون أو مدير نظام، أرغب في إدخال بيانات رأس الرصيد الافتتاحي حتى أتمكن من إنشاء وثيقة رصيد افتتاحي تحتوي على معلوماتها الأساسية قبل إضافة الأصناف والتفاصيل. |
| **Actor** | المستخدم (موظف المخزون / مدير النظام). |
| **Preconditions** | أن يكون المستخدم قد فتح شاشة الأرصدة الافتتاحية بنجاح؛ أن يكون المستخدم لديه صلاحية إدخال البيانات؛ أن تكون الشاشة جاهزة لاستقبال الإدخال. |
| **Trigger** | قيام المستخدم ببدء إنشاء رصيد افتتاحي جديد أو النقر على حقول بيانات الوثيقة لإدخال المعلومات. |
| **Main Flow** | 1. يقوم المستخدم بفتح شاشة الأرصدة الافتتاحية.؛ 2. يعرض النظام قسم بيانات رأس الرصيد `Header`.؛ 3. يقوم المستخدم بإدخال رقم الوثيقة.؛ 4. يقوم المستخدم بتحديد تاريخ الرصيد الافتتاحي.؛ 5. يقوم المستخدم بإدخال اسم المستخدم أو يتم تعبئته تلقائيًا حسب النظام.؛ 6. يقوم المستخدم بإدخال البيان أو الملاحظات الخاصة بالرصيد.؛ 7. يقوم النظام بالتحقق من صحة البيانات المدخلة.؛ 8. يحتفظ النظام بالبيانات المدخلة مؤقتًا لاستخدامها عند إضافة تفاصيل الأصناف. |
| **Alternate Flow A1** | **ترك حقل إلزامي فارغًا:** الشرط: المستخدم لم يدخل أحد الحقول المطلوبة مثل رقم الوثيقة.؛ **الخطوات:** 1. يحاول المستخدم الانتقال للخطوة التالية أو إضافة تفاصيل.؛ 2. يقوم النظام بفحص البيانات.؛ 3. يكتشف النظام وجود حقل ناقص.؛ 4. يعرض رسالة: «يرجى إدخال رقم الوثيقة».؛ **النتيجة:** لا يسمح النظام بالمتابعة حتى استكمال البيانات. |
| **Alternate Flow A2** | **إدخال تاريخ غير صحيح:** الشرط: المستخدم يدخل تاريخًا غير صالح.؛ **الخطوات:** 1. يقوم المستخدم بإدخال التاريخ.؛ 2. يتحقق النظام من القيمة.؛ 3. يكتشف النظام أن التاريخ غير صحيح.؛ 4. يعرض رسالة خطأ.؛ **النتيجة:** يطلب النظام إدخال تاريخ صحيح. |
| **Alternate Flow A3** | **إدخال رقم وثيقة مكرر في حالة تطبيق قاعدة عدم التكرار:** 1. يدخل المستخدم رقم وثيقة موجود مسبقًا.؛ 2. يتحقق النظام من الرقم.؛ 3. يكتشف التكرار.؛ 4. يعرض رسالة: «رقم الوثيقة موجود مسبقًا». |
| **Postconditions** | عند نجاح العملية يتم إنشاء بيانات رأس الرصيد الافتتاحي بشكل مؤقت داخل النظام؛ تصبح بيانات `Header` جاهزة لإضافة تفاصيل الأصناف؛ يظهر للمستخدم نموذج إضافة الأصناف. |
| **Functional Requirements** | يجب أن يسمح النظام بإدخال رقم الوثيقة؛ يجب أن يسمح النظام بتحديد تاريخ الرصيد؛ يجب أن يسمح النظام بإدخال بيانات المستخدم؛ يجب أن يسمح النظام بإضافة بيان أو ملاحظات؛ يجب أن يتحقق النظام من صحة البيانات قبل الانتقال إلى تفاصيل الرصيد؛ يجب الاحتفاظ بالبيانات المدخلة وربطها بتفاصيل الأصناف لاحقًا. |
| **Non-Functional Requirements** | يجب أن تكون حقول الإدخال واضحة وسهلة الاستخدام؛ يجب عرض رسائل التحقق بشكل مفهوم للمستخدم؛ يجب أن تكون الواجهة متوافقة مع اللغة العربية واتجاه `RTL`؛ يجب أن تستجيب الشاشة بسرعة أثناء إدخال البيانات؛ يجب منع إدخال قيم غير صحيحة. |
| **Acceptance Criteria** | عند فتح شاشة الرصيد يستطيع المستخدم إدخال بيانات الرأس؛ جميع الحقول المطلوبة تظهر بشكل واضح؛ يمنع النظام الانتقال عند وجود بيانات ناقصة؛ يتم حفظ البيانات مؤقتًا بعد إدخالها بنجاح؛ تصبح البيانات جاهزة لاستخدامها عند إضافة تفاصيل الأصناف. |
| **Assumptions** | لا يوجد اتصال بقاعدة بيانات، وسيتم الاحتفاظ بالبيانات باستخدام `Mock Data`؛ رقم الوثيقة قد يتم إدخاله يدويًا أو توليده تلقائيًا حسب قرار الفريق؛ بيانات المستخدم قد تكون ثابتة ضمن `Mock Data`؛ هذه الحالة لا تشمل إضافة الأصناف لأنها ستكون في حالة استخدام منفصلة. |

## UC-003 — إضافة صنف إلى بيانات الرصيد الافتتاحي

| الحقل | التحليل |
| --- | --- |
| **Use Case ID** | `UC-003` |
| **Use Case Name** | إضافة صنف إلى بيانات الرصيد الافتتاحي |
| **User Story** | بصفتي موظف مخزون أو مدير نظام، أرغب في إضافة أصناف إلى تفاصيل الرصيد الافتتاحي مع تحديد المخزن والكمية والسعر وتاريخ الصلاحية حتى أتمكن من تسجيل الكميات الموجودة فعليًا في المخازن عند بداية استخدام النظام. |
| **Actor** | المستخدم (موظف المخزون / مدير النظام). |
| **Preconditions** | أن يكون المستخدم قد فتح شاشة الأرصدة الافتتاحية؛ أن تكون بيانات رأس الرصيد الافتتاحي مدخلة أو جاهزة؛ توفر قائمة الأصناف والمخازن الوهمية `Mock Data`. |
| **Trigger** | ضغط المستخدم على زر «إضافة صنف» داخل قسم تفاصيل الرصيد الافتتاحي. |
| **Main Flow** | 1. يقوم المستخدم بالضغط على زر إضافة صنف.؛ 2. يقوم النظام بعرض نموذج إدخال تفاصيل الصنف.؛ 3. يقوم المستخدم باختيار الصنف من قائمة الأصناف.؛ 4. يقوم النظام بعرض اسم الصنف المختار.؛ 5. يقوم المستخدم باختيار المخزن الذي يوجد به الصنف.؛ 6. يقوم المستخدم بإدخال كمية الصنف.؛ 7. يقوم المستخدم بإدخال السعر إذا كان مطلوبًا.؛ 8. يقوم المستخدم بإدخال تاريخ الصلاحية إذا كان موجودًا.؛ 9. يقوم المستخدم بالضغط على زر إضافة.؛ 10. يقوم النظام بالتحقق من صحة البيانات المدخلة.؛ 11. يقوم النظام بإضافة الصنف إلى جدول تفاصيل الرصيد الافتتاحي.؛ 12. يظهر الصنف ضمن قائمة التفاصيل المرتبطة بالوثيقة. |
| **Alternate Flow A1** | **عدم اختيار الصنف:** الشرط: المستخدم يحاول إضافة سجل بدون اختيار صنف.؛ **الخطوات:** 1. يضغط المستخدم إضافة.؛ 2. يتحقق النظام من البيانات.؛ 3. يكتشف عدم وجود صنف.؛ 4. يعرض رسالة: «يرجى اختيار الصنف».؛ **النتيجة:** لا تتم إضافة السطر. |
| **Alternate Flow A2** | **عدم اختيار المخزن:** الشرط: لم يتم تحديد المخزن.؛ **الخطوات:** 1. يحاول المستخدم حفظ السطر.؛ 2. يتحقق النظام من المخزن.؛ 3. يعرض رسالة: «يرجى اختيار المخزن».؛ **النتيجة:** يمنع النظام الإضافة. |
| **Alternate Flow A3** | **إدخال كمية غير صحيحة:** الشرط: إدخال كمية تساوي صفرًا أو أقل. مثال: `Quantity = -5`.؛ **الخطوات:** 1. يتحقق النظام من الكمية.؛ 2. يكتشف أن القيمة غير صحيحة.؛ 3. يعرض رسالة: «يجب أن تكون الكمية أكبر من صفر».؛ **النتيجة:** لا تتم إضافة الصنف. |
| **Alternate Flow A4** | **تكرار نفس الصنف:** الشرط: إضافة نفس الصنف الموجود مسبقًا. مثال: دواء `X`، المخزن الرئيسي، `50`، تاريخ `2027`، ثم دواء `X`، المخزن الرئيسي، `30`، تاريخ `2028`.؛ **الخطوات:** 1. يتحقق النظام من السطر الجديد.؛ 2. يسمح بالإضافة إذا كان الاختلاف في السعر أو تاريخ الصلاحية.؛ **النتيجة:** يتم إضافة السطر كدفعة جديدة. |
| **Postconditions** | بعد نجاح العملية تتم إضافة الصنف إلى تفاصيل الرصيد الافتتاحي؛ يظهر الصنف في جدول التفاصيل؛ يصبح الصنف مرتبطًا بوثيقة الرصيد الحالية؛ يمكن للمستخدم إضافة أصناف أخرى. |
| **Functional Requirements** | يجب أن يوفر النظام زرًا لإضافة صنف جديد؛ يجب أن يعرض النظام قائمة الأصناف المتاحة؛ يجب أن يعرض النظام قائمة المخازن المتاحة؛ يجب أن يسمح بإدخال كمية الصنف؛ يجب أن يسمح بإدخال السعر؛ يجب أن يسمح بإدخال تاريخ الصلاحية؛ يجب إضافة الصنف إلى جدول التفاصيل بعد نجاح التحقق؛ يجب السماح بتكرار الصنف عند اختلاف السعر أو تاريخ الصلاحية. |
| **Non-Functional Requirements** | يجب أن تكون عملية إضافة الصنف سهلة وسريعة؛ يجب أن تكون القوائم واضحة للمستخدم؛ يجب عرض رسائل الخطأ بشكل مفهوم؛ يجب أن تكون الواجهة متوافقة مع اللغة العربية `RTL`؛ يجب أن تعمل العملية بدون إعادة تحميل الصفحة باستخدام `Blazor`. |
| **Acceptance Criteria** | يستطيع المستخدم فتح نموذج إضافة صنف؛ يستطيع اختيار صنف من القائمة؛ يستطيع اختيار مخزن؛ يستطيع إدخال كمية صحيحة؛ يظهر الصنف في جدول التفاصيل بعد الإضافة؛ يمنع النظام إضافة بيانات ناقصة؛ يسمح بتكرار الصنف عند اختلاف السعر أو تاريخ الصلاحية. |
| **Assumptions** | بيانات الأصناف والمخازن يتم توفيرها باستخدام `Mock Data`؛ لا يتم الحفظ في قاعدة بيانات؛ السعر وتاريخ الصلاحية قد يكونان اختياريين حسب نوع الصنف؛ الإضافة تتم داخل الذاكرة أثناء تشغيل التطبيق. |

## UC-004 — اختيار الصنف في بيانات الرصيد الافتتاحي

| الحقل | التحليل |
| --- | --- |
| **Use Case ID** | `UC-004` |
| **Use Case Name** | اختيار الصنف في بيانات الرصيد الافتتاحي |
| **User Story** | بصفتي موظف مخزون أو مدير نظام، أرغب في اختيار الصنف من قائمة الأصناف المتاحة حتى أتمكن من تحديد المنتج الذي سيتم إدخاله ضمن تفاصيل الرصيد الافتتاحي. |
| **Actor** | المستخدم (موظف المخزون / مدير النظام). |
| **Preconditions** | أن يكون المستخدم داخل شاشة إضافة تفاصيل الرصيد الافتتاحي؛ أن تكون قائمة الأصناف متوفرة من `Mock Data`؛ أن يكون النظام جاهزًا لاستقبال اختيار الصنف. |
| **Trigger** | قيام المستخدم بالضغط على حقل اختيار الصنف أو فتح قائمة الأصناف. |
| **Main Flow** | 1. يقوم المستخدم بالضغط على حقل اختيار الصنف.؛ 2. يقوم النظام بعرض قائمة الأصناف المتاحة.؛ 3. يقوم المستخدم بالبحث أو التصفح داخل قائمة الأصناف.؛ 4. يختار المستخدم الصنف المطلوب.؛ 5. يقوم النظام بتحديد الصنف المختار.؛ 6. يعرض النظام اسم الصنف في الحقل.؛ 7. يقوم النظام بربط الصنف مع سطر تفاصيل الرصيد الحالي. |
| **Alternate Flow A1** | **عدم وجود أصناف:** الشرط: قائمة الأصناف فارغة.؛ **الخطوات:** 1. يفتح المستخدم قائمة الأصناف.؛ 2. لا يجد النظام أي بيانات.؛ 3. يعرض رسالة: «لا توجد أصناف متاحة للاختيار».؛ **النتيجة:** لا يمكن إكمال إضافة السطر حتى توفر صنف. |
| **Alternate Flow A2** | **إلغاء اختيار الصنف:** الشرط: المستخدم فتح القائمة ولم يختر صنفًا.؛ **الخطوات:** 1. يغلق المستخدم القائمة.؛ 2. يحتفظ النظام بالقيمة السابقة أو يترك الحقل فارغًا. |
| **Postconditions** | تم اختيار صنف بنجاح؛ تم ربط الصنف بسطر تفاصيل الرصيد؛ أصبح الصنف جاهزًا لاستكمال إدخال باقي البيانات. |
| **Functional Requirements** | يجب عرض قائمة الأصناف للمستخدم؛ يجب السماح بالبحث عن الصنف؛ يجب عرض اسم الصنف وليس الرقم فقط؛ يجب حفظ معرف الصنف داخليًا؛ يجب ربط الصنف بسجل التفاصيل. |
| **Non-Functional Requirements** | يجب أن تكون عملية البحث والاختيار سريعة؛ يجب أن تكون القائمة سهلة الاستخدام؛ يجب عرض أسماء واضحة للأصناف؛ يجب دعم اللغة العربية. |
| **Acceptance Criteria** | تظهر قائمة الأصناف عند الضغط على الحقل؛ يستطيع المستخدم اختيار صنف؛ يظهر اسم الصنف بعد الاختيار؛ لا يظهر للمستخدم رقم الصنف فقط؛ يتم ربط الصنف بالسطر الحالي. |
| **Assumptions** | بيانات الأصناف تأتي من `Mock Data`؛ لكل صنف معرف داخلي يستخدمه النظام؛ لا توجد قاعدة بيانات في هذه المرحلة. |

## UC-005 — اختيار المخزن في بيانات الرصيد الافتتاحي

| الحقل | التحليل |
| --- | --- |
| **Use Case ID** | `UC-005` |
| **Use Case Name** | اختيار المخزن في بيانات الرصيد الافتتاحي |

| **Alternate Flow A1** | **محاولة الحفظ بدون بيانات رأس الرصيد:** الشرط: وجود نقص في بيانات `Header`.؛ **الخطوات:** 1. يضغط المستخدم حفظ.؛ 2. يتحقق النظام من بيانات الوثيقة.؛ 3. يكتشف وجود بيانات ناقصة.؛ 4. يعرض رسالة: «يرجى استكمال بيانات الرصيد الافتتاحي».؛ **النتيجة:** لا يتم تنفيذ الحفظ. |
| **Alternate Flow A2** | **محاولة الحفظ بدون تفاصيل أصناف:** الشرط: الرصيد يحتوي على بيانات الرأس فقط بدون أصناف.؛ **الخطوات:** 1. يضغط المستخدم حفظ.؛ 2. يتحقق النظام من جدول التفاصيل.؛ 3. يجد النظام أن القائمة فارغة.؛ 4. يعرض رسالة: «يجب إضافة صنف واحد على الأقل قبل الحفظ».؛ **النتيجة:** لا يتم حفظ الرصيد. |
| **Alternate Flow A3** | **وجود بيانات تفاصيل غير صحيحة:** الشرط: وجود صنف بدون مخزن أو كمية غير صحيحة.؛ **المثال:** الصنف `Laptop`؛ المخزن غير محدد؛ الكمية `0`.؛ **الخطوات:** 1. يقوم المستخدم بالحفظ.؛ 2. يقوم النظام بفحص التفاصيل.؛ 3. يكتشف خطأ في البيانات.؛ 4. يعرض رسالة توضح المشكلة.؛ **النتيجة:** يطلب النظام تصحيح البيانات. |
| **Alternate Flow A4** | **فشل عملية الحفظ:** الشرط: حدوث خطأ أثناء تخزين البيانات في `Mock Data`.؛ **الخطوات:** 1. يحاول النظام حفظ البيانات.؛ 2. يحدث خطأ.؛ 3. يعرض رسالة: «حدث خطأ أثناء حفظ الرصيد الافتتاحي». |
| **Postconditions** | بعد نجاح العملية يتم حفظ بيانات الرصيد الافتتاحي داخل التطبيق؛ يتم الاحتفاظ ببيانات الرأس والتفاصيل معًا؛ تصبح الوثيقة جاهزة للعرض أو التعديل؛ تظهر رسالة نجاح للمستخدم. |
| **Functional Requirements** | يجب أن يوفر النظام زرًا لحفظ الرصيد الافتتاحي؛ يجب التحقق من اكتمال بيانات الرأس قبل الحفظ؛ يجب التحقق من وجود تفاصيل أصناف قبل الحفظ؛ يجب التحقق من صحة بيانات الكمية والصنف والمخزن؛ يجب حفظ بيانات الرصيد مع تفاصيله؛ يجب عرض رسالة نجاح بعد إتمام الحفظ؛ يجب عرض رسائل خطأ عند فشل عملية الحفظ. |
| **Non-Functional Requirements** | يجب أن تتم عملية الحفظ بسرعة؛ يجب منع فقدان البيانات أثناء العملية؛ يجب أن تكون رسائل الخطأ واضحة للمستخدم؛ يجب أن تكون عملية الحفظ سهلة الاستخدام؛ يجب أن تدعم الواجهة اللغة العربية واتجاه `RTL`. |
| **Acceptance Criteria** | يستطيع المستخدم حفظ الرصيد بعد اكتمال البيانات؛ يمنع النظام الحفظ عند وجود بيانات ناقصة؛ يتم حفظ بيانات الرأس مع تفاصيل الأصناف؛ تظهر رسالة نجاح بعد الحفظ؛ تظهر رسائل واضحة عند وجود أخطاء؛ تبقى البيانات محفوظة داخل التطبيق أثناء التشغيل. |
| **Assumptions** | لا يوجد اتصال بقاعدة بيانات ويتم استخدام `Mock Data`؛ الحفظ يكون مؤقتًا داخل ذاكرة التطبيق؛ لا توجد مرحلة اعتماد أو ترحيل للمخزون في هذه النسخة؛ المستخدم لديه صلاحية حفظ البيانات. |
